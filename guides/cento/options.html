Параметры командной строки

nProbe™ Параметры командной строки Cento кратко описаны ниже. Ту же самую сводку, показанную ниже, можно получить, запустив nProbe™ Cento с аргументом --help. Нетривиальные варианты затем логически перестраиваются и обсуждаются более подробно после краткого изложения.

Интерфейсы

[--interface|-i] <ifname|pcap файл>

nProbe™ Cento поддерживает сетевые адаптеры как с ванильными драйверами, так и с драйверами PF_RING. Интерфейс может быть указан как «-i eth0» (обработка внутри ядра с использованием ванильных драйверов или драйверов, поддерживающих PF_RING) или как «-i zc:eth0» (обход ядра). Префикс zc: сообщает PF_RING использовать модуль Zero копирования (ZC).

nProbe™ Cento также может снабжаться несколькими очередями масштабирования на стороне приема (RSS), доступными с одного или нескольких интерфейсов. Очереди указываются с помощью знака @ между именем интерфейса и номером очереди. Например, следующая команда запускает nProbe™ Cento в 4 очередях ZC интерфейса eth1.

cento -i zc:eth1@0 -i zc:eth1@1 -i zc:eth1@2 -i zc:eth1@3

Те же 4 очереди могут быть обработаны в ядре, если опустить префикс zc: следующим образом:

cento -i eth1@0 -i eth1@1 -i eth1@2 -i eth1@3

nProbe™ Cento для каждого отдельного интерфейса, указанного с помощью -i, запускает два параллельных потока, а именно поток процессора пакетов и поток экспортера потоков. Дополнительные потоки могут быть созданы, как описано ниже.

Количество интерфейсов, а также количество очередей, которые необходимо обработать с помощью nProbe™ Cento, может значительно вырасти. По этой причине допускается компактное обозначение в квадратных скобках для краткого обозначения диапазонов интерфейсов (очередей). Например, используя компактную запись, nProbe™ Cento можно запустить в 4 очередях ZC eth1, описанных выше, как

cento -i zc:eth1@[0-3]

Аналогичным образом можно запустить программное обеспечение на четырех отдельных интерфейсах ZC, как

cento -i zc:eth[0-3]

Выходные очереди

[--balanced-egress-queues|-o] <количество|устройство>

Используя эту опцию nProbe™ Cento создает для каждого интерфейса, отправленного с параметром -i, количество <num> выходных очередей. Альтернативно можно указать список выходных устройств (физических интерфейсов), разделенных запятыми. Исходящий трафик балансируется по исходящим очередям, созданным с помощью кортежа из пяти. Поэтому гарантируется, что все пакеты, принадлежащие данному потоку, будут отправлены в одну и ту же выходную очередь. Подробное описание сбалансированных исходящих очередей приведено в разделе «Исходящие очереди». Ниже приведен лишь краткий пример.

Предполагая, что nProbe™ Cento необходимо настроить для мониторинга двух очередей eth1 ZC, чтобы трафик, поступающий из каждой из них, перенаправлялся в две отдельные выходные очереди, можно использовать следующую команду

cento -i zc:eth1@0 -i zc:eth1@1 --balanced-egress-queues 2

nProbe™ Вывод Cento подтверждает, что трафик будет правильно сбалансирован и перенаправлен в исходящие очереди:

[...]
Initialized global ZC cluster 10
Created interface zc:eth1@0 bound to 0
Reading packets from interface zc:eth1@0...
Created interface zc:eth1@1 bound to 2
Reading packets from interface zc:eth1@1...
Forwarding interface zc:eth1@0 balanced traffic to zc:10@0
Forwarding interface zc:eth1@0 balanced traffic to zc:10@1
[ZC] Egress queue zc:10@0 (0/2) bound to interface zc:eth1@0
[ZC] Egress queue zc:10@1 (1/2) bound to interface zc:eth1@0
Forwarding interface zc:eth1@1 balanced traffic to zc:10@2
Forwarding interface zc:eth1@1 balanced traffic to zc:10@3
[ZC] Egress queue zc:10@2 (0/2) bound to interface zc:eth1@1
[ZC] Egress queue zc:10@3 (1/2) bound to interface zc:eth1@1
[...]

Выходные очереди идентифицируются строкой zc:<идентификатор кластера>:<идентификатор очереди>, например, zc:10@0. Назначенные идентификаторы кластера и очереди выводятся nProbe™ Cento. Выходные очереди могут передаваться в другие приложения, такие как системы обнаружения вторжений (IDS) и системы предотвращения вторжений (IPS). Простой подсчет пакетов можно выполнить с помощью утилиты PF_RING pfcount. Подсчитать пакеты, полученные в очереди ZC 1 в кластере 0, так же просто, как

pfcount -i zc:10@0

Вместо этого для пересылки трафика на физические интерфейсы можно указать список имен интерфейсов, разделенных запятыми:

cento -i zc:eth1 --balanced-egress-queues zc:eth2,zc:eth3

За подробным описанием архитектуры PF_RING мы отсылаем читателя к Руководству пользователя PF_RING, доступному по адресу: https://www.ntop.org/guides/pf_ring

[--aggregated-egress-queue|-F [<dev>]]

nProbe™ Cento может агрегировать трафик, поступающий от каждого входного интерфейса, и перенаправлять его в единую глобальную агрегированную выходную очередь. Другими словами, nProbe™ Cento, запущенный с этой опцией, действует как агрегатор трафика N-to-1. По сути, это «двойной» результат того, что достигается с помощью --balanced-egress-queues. В последнем случае nProbe™ Cento действует как балансировщик трафика 1-N. Подробное описание агрегированных исходящих очередей приведено в разделе «Исходящие очереди». Ниже приводится лишь краткий пример.

Предполагая, что nProbe™ Cento необходимо настроить для объединения 4 очередей eth1 ZC, чтобы трафик, поступающий из каждой из них, был агрегирован в одну выходную очередь, достаточно выполнить следующую команду

cento -izc:eth1@0 -izc:eth1@1 -izc:eth1@2 -izc:eth1@3 --aggregated-egress-queue

nProbe™ Вывод Cento подтверждает, что трафик будет правильно агрегирован в одну очередь, идентифицированную zc:10@0.

[...]
Initialized global ZC cluster 10
Created interface zc:eth1@0 bound to 0
Reading packets from interface zc:eth1@0...
Created interface zc:eth1@1 bound to 2
Reading packets from interface zc:eth1@1...
Created interface zc:eth1@2 bound to 4
Reading packets from interface zc:eth1@2...
Created interface zc:eth1@3 bound to 6
Reading packets from interface zc:eth1@3...
Fwd.ing aggregated traffic to zc:10@0, you can now start your recorder/IDS
[...]

В общем, как уже отмечалось выше, любая выходная очередь идентифицируется строкой zc:<идентификатор кластера>:<идентификатор очереди>, например, zc:10@0.

Для подсчета агрегированного трафика можно использовать утилиту PF_RING pfcount как

pfcount -i zc:10@0

Одна и та же очередь может быть введена в регистраторы трафика, такие как n2disk, а также в IDS/IPS.

nProbe™ Cento также может агрегировать и отправлять входящий трафик на физическое сетевое устройство. В этом случае имя устройства <dev> необходимо указать сразу после опции --aggregated-egress-queue.

[--egress-conf|-e] <файл>

Как агрегированные, так и сбалансированные исходящие очереди позволяют детально контролировать трафик с помощью набора иерархических правил. Правила указываются в виде обычного текста <файл>, который соответствует стандарту INI. Подробное описание формата файла приведено в разделе «Выходные очереди» настоящего руководства.

[--balanced-egress-buffer] <размер буфера>

Когда --balanced-egress-queues используется опция, также можно определить конкретные очереди/интерфейсы назначения для выбранного трафика в файле правил, поставляемом с --egress-conf, дополнительные сведения см. в разделе «Выходящие очереди — правила политики». В этом случае, если трафик выбран протоколом приложения, поскольку механизму DPI может потребоваться несколько пакетов для обнаружения приложения (в зависимости от фактического протокола), начальные пакеты могут не быть доставлены в ожидаемый пункт назначения. Чтобы преодолеть это, --balanced-egress-buffer был введен для хранения пакетов в памяти до тех пор, пока приложение не будет обнаружено, после чего все пакеты пересылаются по назначению. Этот вариант требовал достаточно большого объема памяти, в зависимости от скорости трафика, который выделяется с огромных страниц. Должен быть указан <размер буфера>, который представляет собой максимальное количество пакетов, которые могут быть буферизованы и используются приложением для резервирования памяти огромных страниц при запуске.

Генерация потоков

[--lifetime-timeout|-t] <сек>

nProbe™ Cento считает просроченным и генерирует любой поток, который был активен более <sec> секунд. Если поток по-прежнему активен по истечении <сек> секунд, дальнейшие принадлежащие ему пакеты будут учитываться в новом потоке.

Таймаут времени жизни по умолчанию установлен на 300 секунд.

[--lifetime-perturbation] <сек>

Добавляет случайное возмущение в диапазоне 0–<сек> к вновь созданным потокам, чтобы избежать их одновременного истечения срока действия (в случае длительных потоков). По умолчанию возмущение отключено.

[--idle-timeout|-d] <сек>

nProbe™ Cento считает законченным и генерирует любой поток, который не передавал пакеты в течение <sec> секунд. Если поток все еще активен и будет передавать снова через <сек> секунд, его дальнейшие пакеты будут учитываться в новом потоке.

Это также означает, что, когда это применимо (например, SNMP walk) UDP потоки будут учитываться не на основе 1 пакета/1 потока, а на основе единого глобального потока, который учитывает весь трафик. Преимущество этого заключается в том, что уменьшается общее количество генерируемых потоков и улучшается общая производительность коллектора.

Тайм-аут простоя по умолчанию установлен на 180 секунд.

[--пропустить-фрагменты]

Приказывает nProbe™ Cento отбрасывать фрагментированный IP-трафик. Это особенно полезно в средах со сверхвысокими скоростями, где отслеживание фрагментов может оказаться слишком дорогостоящим.

[--туннель]

Декодирование туннелируемых пакетов.

[--cache-flow-direction|-U]

Для потоков TCP эта опция позволяет кэшировать направления потоков, чтобы они сохранялись в случае длинных потоков.

CPU Родство

[--processing-cores|-g <ядра>]

nProbe™ Cento создает параллельный поток процессора для каждого входного интерфейса. Любой поток процессора обязан обрабатывать все пакеты, связанные с его интерфейсом, и строить соответствующие потоки. Такая конструкция позволяет использовать современные многоядерные многоядерные архитектуры, поскольку потоки могут работать независимо и параллельно для обработки трафика, поступающего от нескольких интерфейсов.

Привязка позволяет пользователю привязать любой поток процессора (и, следовательно, любой интерфейс) к данному ядру. Используя эту опцию, nProbe™ Cento даст указание планировщику операционной системы выполнять потоки процессора на указанных ядрах. Ядра идентифицируются по их идентификаторам. Идентификаторы ядер можно найти непосредственно в /sys/devices.

Например, идентификаторы ядер для 4-ядерного гиперпоточного CPU Intel Xeon E3-1230 v3 можно найти с помощью

~$ cat /sys/devices/system/cpu/cpu*/topology/thread_siblings_list
0,4
1,5
2,6
3,7
0,4
1,5
2,6
3,7

В каждой строке есть два числа: первое — это идентификатор ядра, а второе — связанное с ним гиперпоточное ядро. Строки повторяются два раза, поскольку одна и та же информация содержится как для ядра, так и для связанного с ним гиперпоточного ядра. Используя affinity и идентификаторы ядер, можно значительно оптимизировать использование ядер и гарантировать, что несколько приложений не будут мешать друг другу в высокопроизводительных установках.

Чтобы запустить nProbe™ Cento на двух интерфейсах ZC и привязать потоки процессора к ядрам с идентификаторами 0 и 1 соответственно, можно выполнить следующую команду

cento -i zc:eth0 -i zc:eth1 -g 0,1

[--exporting-cores|-G <ядра>]

nProbe™ Cento создает поток экспорта для каждого входного интерфейса. Любой поток экспорта занимается экспортом потоков в соответствии с предоставленными пользователем параметрами. Примерами потоков экспортеров являются экспортеры Netflow V5/V5. То же описание, данное для параметра --processing-cores, применяется здесь для установки сходства ядер экспортера.

[--monitor-aggregator-core|-M <ядро>]

Эта опция регулирует привязку потоков экспорта потока nProbe™ Cento к виртуальному интерфейсу мониторинга для видимости трафика (см. опцию --monitor).

[--timer-core|-N <ядро>]

Эта опция регулирует привязку потока nProbe™ Cento, который отслеживает время. Сохранение этого потока в слегка загруженном ядре позволяет получать очень точные временные метки, особенно когда аппаратные временные метки недоступны.

Настройки экспорта потоков

Эти настройки указывают потокам экспортера интерфейса на выходной формат.

[--dump-path|-P] [<d1>:<d2>:<ml>:]<dir>

nProbe™ Cento экспортирует потоки в простом текстовом формате, разделенном вертикальной чертой, если указан --dump-path. Каждый интерфейс экспортируется в подкаталог <dir>, имеющий то же имя, что и интерфейс. Каждый подкаталог содержит дерево каталогов, организованное во вложенной форме «временной шкалы»: год, месяц, день, час дня, минуты часа. Подкаталоги, являющиеся «листьями» этого дерева, содержат настоящие текстовые файлы.

Дерево подкаталогов заполняется в соответствии с параметрами <d1>, <d2> и <ml>. В частности, nProbe™ Cento создает новый подкаталог каждые <d1> секунд. Текстовый файл содержит не более <ml> потоков, по одному на строку. Если за время менее <d2> секунд будет записано более <ml> потоков, создается один или несколько файлов. Если за <d2> секунд было записано менее <ml> потоков, файл потоков закрывается и создается новый.

Например, чтобы захватить данные из двух очередей eth1 ZC и записать собранные потоки в /tmp, можно использовать следующую команду:

cento -izc:eth1@0 -izc:eth1@1 -P 300:50:20000:/tmp/

Команда предписывает nProbe™ Cento сбрасывать потоки в /tmp с дополнительными условиями, которые: Каждый файл потоков не должен содержать более 20 000 потоков и не должен содержать потоки с трафиком более 50 секунд. Каждый подкаталог не должен содержать более 300 секунд трафика.

nProbe™ Вывод Cento подтверждает, что он будет использовать два подкаталога в /tmp, по одному для каждого интерфейса.

[...]
Dumping flows onto /tmp/zc_eth1@0
Dumping flows onto /tmp/zc_eth1@1
[...]

Пример полученной структуры каталогов следующий:

~/ find  /tmp/zc_eth1\@0/*
/tmp/zc_eth1@0/2016
/tmp/zc_eth1@0/2016/05
/tmp/zc_eth1@0/2016/05/04
/tmp/zc_eth1@0/2016/05/04/18
/tmp/zc_eth1@0/2016/05/04/18/1462379942_0.txt
/tmp/zc_eth1@0/2016/05/04/18/1462380145_0.txt
/tmp/zc_eth1@0/2016/05/04/18/1462379214_0.txt
/tmp/zc_eth1@0/2016/05/04/18/1462379603_0.txt
/tmp/zc_eth1@0/2016/05/04/18/1462379881_0.txt

Значение по умолчанию для <d1> — 300 секунд. Значение по умолчанию для <d2> — 60 секунд. Значение по умолчанию для <ml> составляет 10 000 секунд.

[--dump-compression <режим>]

nProbe™ Cento может экспортировать потоки в сжатые текстовые файлы при использовании с опцией --dump-path. Формат сжатия дампа контролируется с помощью этой опции путем выбора <mode>.

<mode> может иметь следующие значения: - n: без сжатия (по умолчанию) -g: сжатие gzip - b: сжатие bzip

[--v5|-5 <хост:порт>]

Экспортирует NetFlow в пункт назначения <хост:порт>, используя версию 5. Список, разделенный запятыми, можно использовать для балансировки нагрузки между несколькими пунктами назначения.

[--v9|-9 <хост:порт>]

Экспортирует NetFlow в пункт назначения <хост:порт>, используя версию 9. Список, разделенный запятыми, можно использовать для балансировки нагрузки между несколькими пунктами назначения.

[--ipfix|-I <хост:порт>]

Экспортирует IPFIX в пункт назначения <хост:порт>. Список, разделенный запятыми, можно использовать для балансировки нагрузки между несколькими пунктами назначения.

[--zmq <конечная точка>]

Потоки могут быть экспортированы с помощью nProbe™ Cento через ZMQ в заданную <конечную точку>. Обычно эта <конечная точка> представляет собой экземпляр ntopng, который непрерывно собирает полученные потоки для дальнейшего анализа и визуализации. Также поддерживается список конечных точек, разделенных запятыми, для экспорта потока балансировки нагрузки на несколько конечных точек. Примечание: используется режим зонда, настройте ntopng как коллектор. Подробное описание варианта использования см. в разделе «Интеграция с ntopng».

[--zmq-ключ-шифрования <публичный ключ>]

Потоки, экспортированные через ZMQ с помощью nProbe™ Cento, шифруются с использованием шифрования CURVE. <pub key> — это открытый ключ, сгенерированный самим ntopng при запуске с --zmq-encryption и отображается на странице состояния интерфейса ZMQ.

Если этот параметр не указан, nProbe™ Cento возвращается к общедоступному встроенному ключу по умолчанию, чтобы потоки по-прежнему шифровались, а не отправлялись в открытом виде. Этот ключ по умолчанию предотвращает только случайное раскрытие открытого текста в сети и не обеспечивает реальной конфиденциальности, поскольку он общеизвестен и доступен каждой установке Cento/ntopng, в которой не настроен выделенный ключ: его необходимо заменить настройкой выделенной пары ключей для любого развертывания, требующего реальной безопасности. См. ntopng документация для полного описания того, как настроить шифрование ZMQ между Cento и ntopng.

[--zmq-прямое сопоставление]

Когда несколько --zmq указаны конечные точки и несколько интерфейсов, эта опция сопоставляет каждый интерфейс непосредственно с соответствующей конечной точкой ZMQ (первый интерфейс с первой конечной точкой, второй интерфейс со второй конечной точкой и т. д.). Без этой опции потоки от всех интерфейсов распределяются по всем конечным точкам ZMQ.

Пример

cento -i zc:eth1@[0-1] --zmq tcp://127.0.0.1:5556 --zmq tcp://127.0.0.1:5557 --zmq-direct-mapping

[--zmq-только статистика]

Экспортируйте только периодическую статистику интерфейса (без потоков) в --zmq конечные точки. Это полезно, когда потоки доставляются к коллекторам, отличным от ntopng, через другой канал. Например, при экспорте в Kafka или NetFlow, хотя вы все равно хотите использовать ntopng для мониторинга приложения через ZMQ и получения статистики обработки пакетов и потока экспорта.

[--tcp <адрес>:<порт>]

Потоки могут быть экспортированы с помощью nProbe™ Cento в формате JSON через TCP на заданный сервер, указав <адрес> и <порт>. Вместо цифровых клавиш можно использовать метки, добавив опцию --json-метки.

[--kafka <брокеры>;<тема>[;<ack>;<compr>]

nProbe™ Cento может экспортировать потоки в один или несколько Kafka <брокеров>, которые отвечают за данную <тему> в кластере. Хотя тема представляет собой обычную текстовую строку, брокеры Kafka должны быть указаны в виде списка, разделенного запятыми, в соответствии со следующим форматом.

<host1>[:<port1>],<host2>[:<port2>]

Первоначально nProbe™ Cento пытается связаться с одним или несколькими указанными пользователем брокерами для получения метаданных кластера Kafka. Метаданные включают, среди прочего, список доступных в кластере брокеров, отвечающих за заданную пользователем тему. Как только список брокеров, полученный с помощью метаданных, станет доступен, nProbe™ Cento начнет экспортировать в них потоки.

Пользователь также может принять решение о сжатии данных, указав в <compr> одно из значений none, gizp и snappy. Кроме того, политику <ack> можно указать следующим образом: - <ack> = 0: не ждать подтверждений. - <ack> = 1: получать ACK только от лидера Kafka. - <ack> = -1: получить подтверждение от каждой реплики.

Пример

Предполагая, что на локальном порту 2181 имеется Zookeeper, который управляет кластером Kafka, можно запросить создание новой темы Kafka. Допустим, тема называется «topicFlows», и ее нужно разделить на три раздела с коэффициентом репликации два. Команда, которая должна быть выдана, следующая

bin/kafka-topics.sh --zookeeper localhost:2181 --create --topic topicFlows \
     --partitions 3 --replication-factor 2

Теперь, когда тема Kafka создана, можно запустить nProbe™ Cento и указать экземпляру экспортировать в тему Kafka «topicFlows». Мы также сообщаем экземпляру список из трех брокеров, работающих на локальном хосте (на портах 9092, 9093 и 9094 соответственно), которые будут запрошены в начале для получения метаданных kafka кластера/темы.

cento --kafka “127.0.0.1:9092,127.0.0.1:9093,127.0.0.1:9094;topicFlows"

На данный момент экземпляр nProbe™ Cento активно экспортирует потоки в кластер Kafka. Чтобы убедиться, что все работает правильно, можно удалить сообщения из темы Kafka с помощью следующей команды

bin/kafka-console-consumer.sh --zookeeper localhost:2181 --topic topicFlows\
     --from-beginning

[--avro]

При экспорте потоков в Kafka, nProbe™ Cento по умолчанию использует кодировку JSON. При желании можно включить кодировку Avro при экспорте данных в Kafka с помощью --avro вариант.

[--шаблон]

В отличие от nProbe™ Pro/Enterprise, nProbe™ Cento использует фиксированный шаблон при экспорте данных Netflow v5/v9/IPFIX, однако при экспорте в ZMQ, Kafka (--kafka) или TCP (--tcp) с использованием Кодировка JSON или Avro, nProbe™ Cento обеспечивает некоторую гибкость с возможностью выбора шаблона экспорта, аналогично nProbe™ Pro/Enterprise (но с ограниченным набором информационных элементов). Если --шаблон опция не указана, используется шаблон по умолчанию, совместимый с ntopng.

В этой конфигурации nProbe™ Cento также предоставляет возможность:

  • определить псевдонимы, то есть переименовывать информационный элемент (например, L7_PROTO в APPLICATION_PROTOCOL)

  • определить пользовательские информационные элементы, что означает добавление новых полей с жестко запрограммированными значениями (например, DOMAIN с типом «строка» и значением «example.local»).

Псевдонимы можно определить, используя приведенный ниже синтаксис при перечислении информационных элементов в шаблоне:

%ORIGINAL_NAME=>NEW_NAME

Пример (проверьте определение псевдонима APPLICATION_PROTOCOL):

cento -i eno1 --kafka “127.0.0.1:9092,127.0.0.1:9093,127.0.0.1:9094;topicFlows" --json-labels --template "%SRC_VLAN %SRC_MAC %DST_MAC %IP_PROTOCOL_VERSION %IPV4_SRC_ADDR %IPV4_DST_ADDR %IPV6_SRC_ADDR %IPV6_DST_ADDR %EXPORTER_IPV4_ADDRESS %DIRECTION %INPUT_SNMP %OUTPUT_SNMP %SRC_TO_DST_PKTS %SRC_TO_DST_BYTES %DST_TO_SRC_PKTS %DST_TO_SRC_BYTES %FIRST_SWITCHED %LAST_SWITCHED %L4_SRC_PORT %L4_DST_PORT %PROTOCOL %L7_PROTO=>APPLICATION_PROTOCOL %L7_PROTO_NAME=>APPLICATION_PROTOCOL_NAME"

Пример с форматом Avro (проверьте определение псевдонима APPLICATION_PROTOCOL):

cento -i eno1 --kafka “127.0.0.1:9092,127.0.0.1:9093,127.0.0.1:9094;topicFlows" --avro --template "%SRC_VLAN %SRC_MAC %DST_MAC %IP_PROTOCOL_VERSION %IPV4_SRC_ADDR %IPV4_DST_ADDR %IPV6_SRC_ADDR %IPV6_DST_ADDR %EXPORTER_IPV4_ADDRESS %DIRECTION %INPUT_SNMP %OUTPUT_SNMP %SRC_TO_DST_PKTS %SRC_TO_DST_BYTES %DST_TO_SRC_PKTS %DST_TO_SRC_BYTES %FIRST_SWITCHED %LAST_SWITCHED %L4_SRC_PORT %L4_DST_PORT %PROTOCOL %L7_PROTO=>APPLICATION_PROTOCOL %L7_PROTO_NAME=>APPLICATION_PROTOCOL_NAME"

ClickHouse Настройки экспорта

[--clickhouse] <хост[:порт[s]]>

Экспорт выполняется в базу данных ClickHouse на указанном хосте и порту. Порт относится к порту собственного протокола ClickHouse TCP (по умолчанию: 9000). Добавить s на номер порта, чтобы включить шифрование SSL для соединения.

Данные потока, экспортированные в ClickHouse, совместимы с форматом дампа потока ntopng, что позволяет ntopng напрямую читать записи потока, созданные nProbe™ Cento. См. ClickHouse Экспорт раздел для подробного описания этой интеграции.

Примеры:

cento -i zc:eth1 --clickhouse 127.0.0.1
cento -i zc:eth1 --clickhouse 192.168.1.1:9000s

[--clickhouse-dbname] <имя>

ClickHouse имя базы данных. По умолчанию: ntopng.

[--clickhouse-auth] <пользователь:пароль>

ClickHouse учетные данные аутентификации в формате user:password. По умолчанию: default (ClickHouse пользователь по умолчанию без пароля).

[--clickhouse-идентификатор-интерфейса] <id>

ntopng идентификатор интерфейса для экспортируемых потоков. Этот идентификатор используется ntopng для идентификации интерфейса, создавшего потоки. По умолчанию: 0.

Разные настройки

[--черные списки] <файл>

В указанном <файле> содержится список файлов (разделенных возвратом каретки), содержащих IP-адреса, занесенные в черный список. Пример: если <файл> содержит следующие строки

/home/cento/blacklist-file1.txt
/home/cento/blacklist-file2.txt
/home/cento/blacklist-file3.txt

cento откроет все файлы и загрузит прилагаемые IP-адреса (поддерживаются как IPv4, так и IPv6). Формат файла черного списка содержит IP-адреса с необязательным символом CIDR. Пример: 1.2.3.4 и 192.168.1.0/24 являются действительными IP-адресами. Если поток (IP-адрес источника или назначения) будет соответствовать хотя бы одному IP-адресу из списка, поток считается занесенным в черный список и не будет перенаправлен (в случае, если cento был запущен во встроенном режиме).

[--dpi-уровень|-D] <уровень>

Эта опция включает глубокую проверку пакетов (DPI) для потоков. DPI пытается обнаружить протоколы приложений уровня 7, просматривая содержимое пакетов, а не просто используя протоколы и порты уровня 4. Поскольку DPI является дорогостоящей операцией в высокоскоростных средах, nProbe™ Cento может опционально работать в режиме µ-DPI, который повышает производительность за счет сосредоточения внимания только на наиболее распространенных протоколах уровня 7.

<уровень> используется для указания версии DPI, которую необходимо активировать:

  • 0: DPI отключено

  • 1: включить uDPI (устарело, используйте -D 2)

  • 2: включить nDPI (полноценный движок nDPI)

[--активный-опрос|-a]

Включает активный опрос пакетов. При использовании этой опции nProbe™ процессы Cento будут активно проверять наличие новых пакетов, а не использовать механизмы опроса или спящие режимы.

[--не-отбрасывать-привилегии|-z]

По умолчанию nProbe™ Cento удаляет текущие права пользователя, чтобы гарантировать, что процесс запускается с минимально возможным набором разрешений. Эта опция предотвращает потерю привилегий.

[--pid-file|-p <путь>]

Запишите идентификатор процесса в указанный файл

[--hash-size|-w] <размер>

Устанавливает размер хеша кэша потока для каждого интерфейса. Размер указывается с помощью значения, за которым может следовать суффикс «MB». Если суффикс не указан, значение интерпретируется как количество сегментов. Если указан суффикс, то значение интерпретируется как размер кэша потока в памяти.

По умолчанию: 512000 [оценка используемой хэш-памяти 144,5 MB]

[--max-hash-size|-W] <размер>

Устанавливает максимальное количество активных хэш-корзин (по умолчанию — 2 миллиона). Обычно значение -W должно быть как минимум в два раза больше значения -w. Обратите внимание, что в дополнение к активным сегментам потока существуют экспортируемые потоки, поэтому в общей сложности вы можете иметь более -W активных потоков. Эта опция хороша для ограничения памяти, используемой cento, даже в худшем случае (почти) бесконечного числа потоков (например, в случае DoS-атаки).

[--redis|-R] <хост[:порт][@db-id]>

Redis Хост БД[:порт][@идентификатор базы данных]. Redis необходимо использовать, когда используется REST API.

[--демон|-b]

Запускает программное обеспечение в режиме демона.

[--версия]

Распечатайте версию и идентификатор системы.

[--проверить-лицензию]

Проверяет, присутствует ли и действительна лицензия.

[--проверка-обслуживание]

Проверяет статус обслуживания для указанной лицензии.

[--local-nets|-L] <локальные сети>

Список локальных сетей (по умолчанию: адрес не определен). Пример: -L «192.168.0.0/24,172.16.0.0/16».

[--banned-hosts|-B] <путь>

nProbe™ Cento имеет функцию запрета хостов, которую можно включить с помощью этой опции. Список запрещенных хостов должен быть указан по одному в строке в текстовом файле, расположенном по адресу <путь>. Требуется двигатель µ-nDPI.

Например, чтобы запретить facebook.com и google.com через интерфейс eth0, необходимо создать текстовый файл, скажем, Banned.txt, со следующими двумя строками:

google.com
facebook.com

Затем запустите nProbe™ Cento как

cento -ieth0 -D 1 -B /tmp/banned.txt
