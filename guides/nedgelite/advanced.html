Расширенные функции

В этом разделе описаны расширенные функции nEdge Lite и методы оптимизации для опытных пользователей.

Многоочередная обработка

nEdge Lite поддерживает распределение обработки пакетов по нескольким ядрам CPU с использованием нескольких экземпляров NFQUEUE.

Настройка нескольких очередей

Конфигурация iptables:

# Configure 4 queues with CPU fanout
sudo iptables -t mangle -A PREROUTING -j CONNMARK --restore-mark
sudo iptables -t mangle -A PREROUTING -m mark --mark 2 -j DROP
sudo iptables -t mangle -A PREROUTING -m mark --mark 0 \
  -j NFQUEUE --queue-balance 0:3 --queue-cpu-fanout
sudo iptables -t mangle -A POSTROUTING -j CONNMARK --save-mark

Запустите nEdge Lite:

sudo nedgelite -q 0:4 -z tcp://127.0.0.1:1234

Это создает 4 потока, каждый из которых обрабатывает одну очередь (0, 1, 2, 3).

Преимущества производительности

  • Параллельная обработка: Распределяет проверку пакетов по ядрам CPU.

  • Более высокая пропускная способность: линейно масштабируется в зависимости от количества очередей (вплоть до доступных ядер).

  • Меньшая задержка: Сокращает время обработки каждого пакета.

Оптимальное количество очередей

Рекомендуется:

# Use number of CPU cores
CORES=$(nproc)
sudo nedgelite -q 0:$CORES -z tcp://127.0.0.1:1234

Соображения:

  • Больше очередей = больше потоков = выше использование CPU

  • Уменьшение отдачи за пределами количества физических ядер

  • Рассмотрите возможность использования гиперпоточности и других рабочих нагрузок.

CPU Родство

Прикрепите потоки nEdge Lite к определенным ядрам CPU для лучшей локальности кэша:

# Pin to cores 0-3
sudo taskset -c 0-3 nedgelite -q 0:4 -z tcp://127.0.0.1:1234

Оптимизация производительности

Настройка системы

Увеличение размера таблицы Conntrack:

# For high connection counts
sudo sysctl -w net.netfilter.nf_conntrack_max=1048576

# Make persistent
echo "net.netfilter.nf_conntrack_max=1048576" | \
  sudo tee -a /etc/sysctl.conf

Настройте таймауты Conntrack:

# Reduce TCP established timeout
sudo sysctl -w net.netfilter.nf_conntrack_tcp_timeout_established=3600

# Reduce TCP close-wait timeout
sudo sysctl -w net.netfilter.nf_conntrack_tcp_timeout_close_wait=30

Увеличить буфер NFQUEUE:

# In iptables rule
sudo iptables -t mangle -A PREROUTING -m mark --mark 0 \
  -j NFQUEUE --queue-num 0 --queue-bypass --queue-size 4096

Управление памятью

Мониторинг использования памяти:

# Check nEdge Lite memory usage
ps aux | grep nedgelite
pmap $(pidof nedgelite)

Размер хеша потока: хеш-таблица потока фиксируется во время компиляции. При очень большом количестве потоков рассмотрите возможность увеличения размера хэш-таблицы в исходном коде.

IPv6 Поддержка

nEdge Lite поддерживает проверку пакетов IPv6 наряду с IPv4.

Включение IPv6

Примеры сценариев, описанные в Кратком руководстве, уже поддерживают IPv6, его можно включить, добавив параметр -6.

Загрузите модуль IPv6 Conntrack:

sudo modprobe nf_conntrack_ipv6

Настройте ip6tables:

sudo ip6tables -t mangle -A PREROUTING -j CONNMARK --restore-mark
sudo ip6tables -t mangle -A PREROUTING -m mark --mark 2 -j DROP
sudo ip6tables -t mangle -A PREROUTING -m mark --mark 0 -j NFQUEUE --queue-num 0
sudo ip6tables -t mangle -A POSTROUTING -j CONNMARK --save-mark

Запустите nEdge Lite:

Никаких специальных опций не требуется. nEdge Lite автоматически обрабатывает как IPv4, так и IPv6.

sudo nedgelite -q 0 -z tcp://127.0.0.1:1234

IPv6 Соображения

  • Экспорт потока: потоки IPv6 экспортируются в ntopng, как IPv4

  • Правила политики: пулы IP-адресов могут включать диапазоны IPv6 CIDR.

Пользовательская конфигурация nDPI

nDPI поддерживает определения пользовательских протоколов через nDPI API. Подробности см. в документации nDPI.

Чувствительность обнаружения

Некоторые протоколы имеют настраиваемые пороговые значения обнаружения. Обычно они устанавливаются в функциях обнаружения протокола nDPI.

Интеграция формирования трафика

Хотя сам nEdge Lite не осуществляет формирование трафика, он может интегрироваться с Linux tc (контроль трафика).

Использование CONNMARK для tc

Значения CONNMARK nEdge Lite могут использоваться tc для применения политик QoS:

# Create tc classes
sudo tc qdisc add dev eth0 root handle 1: htb default 30
sudo tc class add dev eth0 parent 1: classid 1:1 htb rate 100mbit
sudo tc class add dev eth0 parent 1:1 classid 1:10 htb rate 80mbit
sudo tc class add dev eth0 parent 1:1 classid 1:20 htb rate 20mbit

# Use connmark to classify traffic
sudo tc filter add dev eth0 parent 1: protocol ip prio 1 \
  handle 1 fw classid 1:10  # High priority (mark=1)

sudo tc filter add dev eth0 parent 1: protocol ip prio 2 \
  handle 2 fw classid 1:20  # Low priority (mark=2)

Этикетки подключения

В дополнение к метке пропуска/отключения nEdge Lite может помечать каждое соединение с помощью conntrack. метки (connlabels), описывающие то, что обнаружил nDPI: протоколы, категории и риски потока. Метки хранятся в записи conntrack, поэтому любое правило iptables может соответствовать им с помощью connlabel сопоставление, например, для удаления, регистрации или маркировки трафика данного приложения независимо от политик nEdge Lite.

Ядро предоставляет 128 бит меток на соединение, а nDPI обнаруживает несколько сотен протоколы. Файл карты меток выбирает протоколы, категории и риски, представляющие интерес, и присваивает каждому из них бит метки.

Файл карты меток

Карта меток представляет собой текстовый файл с одним сопоставлением на строку; # начинает комментарий:

<bit> protocol <name|id>                     [<label>]
<bit> category <name|id>                     [<label>]
<bit> risk     <NDPI_xxx code|short name|id> [<label>]
<bit> over                                   [<label>]

  • <bit>: бит метки, 0–127.

  • protocol: nDPI имя или идентификатор протокола (см. nedgelite -H). И мастер, и протокол приложения совпадают, поэтому TLS соответствует TLS.Google тоже. Unknown совпадения с потоками nDPI не удалось обнаружить.

  • category: nDPI название или идентификатор категории (например, SocialNetwork, Streaming; видеть nedgelite -H). Имена, содержащие пробелы (User custom category N) должен быть указан по идентификатору.

  • risk: nDPI риск потока, т.к. NDPI_xxx код (например. NDPI_TLS_SELFSIGNED_CERTIFICATE), короткое имя (например, non_standard_port) или идентификатор (см. nedgelite -H).

  • over: устанавливается для каждого потока после завершения обнаружения.

  • <label>: необязательное имя бита в connlabel.conf. По умолчанию он генерируется из первого отображения бита: NDPI-<PROTOCOL>, NDPI-CAT-<CATEGORY>, NDPI-RISK-<RISK> или NDPI-OVER (прописные буквы, остальные символы заменены на -). Этикетки могут содержать только буквы, цифры и - (а connlabel.conf ограничение).

Имена не чувствительны к регистру. Несколько отображений могут использовать один и тот же бит: бит устанавливается, когда любой из них совпадает. Потоки, не соответствующие никакому сопоставлению, не помечаются (если только over используется). О любой ошибке в файле (неизвестное имя, бит вне диапазона, неверный формат строки) сообщается с помощью его номер строки, и nEdge Lite не запускается.

Пример (/etc/nedgelite/labels.conf):

0   over

# Protocols
1   protocol  TLS
2   protocol  QUIC
3   protocol  BitTorrent
4   protocol  Facebook   FB
5   protocol  Instagram
6   protocol  TikTok

# Categories
10  category  SocialNetwork SOCIAL
11  category  Streaming

# Flow risks
20  risk      NDPI_TLS_SELFSIGNED_CERTIFICATE
21  risk      non_standard_port

Включение ярлыков

  1. Генерировать connlabel.conf с карты и установите его как /etc/xtables/connlabel.conf, чтобы iptables и conntrack могли ссылаться на метки по имя ( /etc/xtables каталог обычно не существует и его необходимо создать). Повторяйте этот шаг при каждом изменении карты.

    nedgelite -L /etc/nedgelite/labels.conf -o /tmp
sudo mkdir -p /etc/xtables
sudo cp /tmp/connlabel.conf /etc/xtables/connlabel.conf

    В примере карты выше сгенерированный файл:

    0 NDPI-OVER
1 NDPI-TLS
2 NDPI-QUIC
3 NDPI-BITTORRENT
4 FB
5 NDPI-INSTAGRAM
6 NDPI-TIKTOK
10        SOCIAL
11        NDPI-CAT-STREAMING
20        NDPI-RISK-TLS-SELFSIGNED-CERT
21        NDPI-RISK-NON-STANDARD-PORT

    Примечание

    nftables читает метки из /etc/connlabel.conf вместо. При использовании ct label в правилах nft установите и туда тот же файл (например, как символическую ссылку на /etc/xtables/connlabel.conf).

  2. Загрузите хотя бы один connlabel правило. Ядро резервирует пространство меток только для связи, созданные во время connlabel правило загружено: без него, метки устанавливаются nEdge Lite молча отбрасываются. Правила надо добавить после настройка сетевого фильтра сценарии (bridge_setup.sh и default_setup.sh очистить таблицы iptables).

    Любое правило, использующее connlabel достаточно совпадения, включая правило «только совпадение» без цель (пакет продолжается без изменений):

    sudo modprobe xt_connlabel
sudo iptables -t mangle -I PREROUTING -m connlabel --label NDPI-OVER

    Правила, действующие на метки, можно добавлять по мере необходимости, например:

    # Drop BitTorrent and social network traffic
sudo iptables -A FORWARD -m connlabel --label NDPI-BITTORRENT -j DROP
sudo iptables -A FORWARD -m connlabel --label SOCIAL -j DROP

# Log connections with a self-signed TLS certificate
sudo iptables -A FORWARD -m connlabel --label NDPI-RISK-TLS-SELFSIGNED-CERT \
  -j LOG --log-prefix "self-signed: "

    Связи, которые уже существовали, когда впервые connlabel правило было загружено, не может быть помечены. Очистите таблицу conntrack, чтобы они были воссозданы (это также сбрасывает их отметка прохождения/отсутствия, чтобы они были проверены еще раз):

    sudo conntrack -F

  3. Запустите nEdge Lite с помощью -L (или --labels=/etc/nedgelite/labels.conf в файл конфигурации):

    sudo nedgelite -q 0 -L /etc/nedgelite/labels.conf

    Когда nEdge Lite работает как служба systemd, сценарий установки выполняется каждый раз. запуск службы и очистка правил меток. Добавьте их обратно из дроп-ина, чей ExecStartPre команды запускаются после команд службы (т. е. после установки скрипт) и до запуска nEdge Lite:

    sudo systemctl edit nedgelite

    [Service]
ExecStartPre=/usr/sbin/iptables -t mangle -I PREROUTING -m connlabel --label NDPI-OVER
ExecStartPre=/usr/sbin/iptables -A FORWARD -m connlabel --label SOCIAL -j DROP

  4. Проверьте метки, присвоенные соединениям:

    sudo conntrack -L -o labels

    Метки сообщаются по имени в конце каждой записи после отметки:

    tcp      6 431996 ESTABLISHED src=192.168.1.20 dst=157.240.231.35 sport=52814 dport=443 packets=42 bytes=6120 src=157.240.231.35 dst=192.168.1.20 sport=443 dport=52814 packets=55 bytes=48211 [ASSURED] mark=1 use=1 labels=NDPI-OVER,NDPI-TLS,FB,SOCIAL
tcp      6 431990 ESTABLISHED src=192.168.1.31 dst=203.0.113.7 sport=40122 dport=8443 packets=12 bytes=1830 src=203.0.113.7 dst=192.168.1.31 sport=8443 dport=40122 packets=10 bytes=4420 [ASSURED] mark=1 use=1 labels=NDPI-OVER,NDPI-TLS,NDPI-RISK-TLS-SELFSIGNED-CERT,NDPI-RISK-NON-STANDARD-PORT

    Только биты, названные в /etc/xtables/connlabel.conf показаны. Связи с данным метка может быть указана с помощью -l:

    sudo conntrack -L -o labels -l SOCIAL

Примечания

  • Метки устанавливаются один раз для каждого соединения после завершения обнаружения nDPI вместе с отметка прохождения/отсутствия. На пакеты, которыми обменивались до этого момента, правила меток не влияют.

  • Метки не зависят от политик nEdge Lite: соединение, разорванное политикой, также помечаются, и правила меток применяются поверх вердикта политики.

  • Чтобы обеспечить трафик только с помощью правил меток, просто не настраивайте политики удаления: без -r и -p nEdge Lite использует встроенную политику передачи всех данных. Связи все еще помечаются как пройденные после завершения обнаружения, что необходимо для прекращения отправки их в nEdge Lite, поэтому сохраняйте правила отметок, установленные сценариями установки.

  • Маркированы только соединения TCP и UDP; широковещательный и многоадресный трафик пропускается.

  • Метки записываются в запись conntrack через netlink, что требует, чтобы запись была уже подтверждено ядром. Потоки, обнаруженные в самом первом пакете (например, короткие UDP обмены, такие как DNS), поэтому могут оставаться немаркированными; с -v Журналы nEdge Lite Unable to set flow label для них.

Расширенная конфигурация режима моста

VLAN Поддержка

nEdge Lite работает с трафиком с тегами VLAN в режиме моста:

# Create bridge
sudo ip link add name br0 type bridge
sudo ip link set dev br0 up

# Add VLAN interfaces
sudo ip link add link eth0 name eth0.10 type vlan id 10
sudo ip link add link eth0 name eth0.20 type vlan id 20
sudo ip link set dev eth0.10 master br0
sudo ip link set dev eth0.20 master br0
sudo ip link set dev eth0.10 up
sudo ip link set dev eth0.20 up

Настраиваем iptables для моста:

sudo iptables -t mangle -A PREROUTING -i br0 -j CONNMARK --restore-mark
sudo iptables -t mangle -A PREROUTING -i br0 -m mark --mark 0 \
  -j NFQUEUE --queue-num 0
sudo iptables -t mangle -A POSTROUTING -o br0 -j CONNMARK --save-mark

Отладка и разработка

Подробное ведение журнала

Включите подробное ведение журнала:

sudo nedgelite -q 0 -z tcp://127.0.0.1:1234 -v

Дампы ядра

Включите дампы ядра для отладки сбоев:

ulimit -c unlimited
sudo sysctl -w kernel.core_pattern=/tmp/core-%e-%p-%t

Работа под отладчиком

sudo gdb --args nedgelite -q 0 -z tcp://127.0.0.1:1234 -v

Интеграция захвата пакетов

Захват пакетов для автономного анализа:

# Capture packets going to NFQUEUE
sudo tcpdump -i eth0 -w /tmp/capture.pcap

# Analyze with Wireshark or tcpdump
tcpdump -r /tmp/capture.pcap -n

Лучшие практики для производства

  1. Используйте несколько очередей: Распределить нагрузку по ядрам CPU.

  2. Мониторинг производительности: просмотр CPU, памяти и глубины очереди.

  3. Интервал обновления настройки: Балансируйте видимость в реальном времени и производительность.

  4. Включить обход очереди: Предотвратить потерю пакетов в случае сбоя nEdge Lite.

  5. Регулярное техническое обслуживание: Обновление nDPI для новых протоколов.

  6. Политики резервного копирования: Хранить файлы политики под контролем версий.

  7. Тестовые изменения: сначала проверьте изменения политики в тестовой среде.

  8. Мониторинг потерянных потоков: Убедитесь, что законный трафик не заблокирован.

  9. Планирование мощности: Выбор аппаратного обеспечения для пиковых нагрузок трафика.
