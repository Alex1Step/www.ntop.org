Балансировка нагрузки/RSS

Обработка трафика от сетевого адаптера с использованием одного потока требует одно ядро CPU, чтобы поддерживать скорость входящего трафика. По высоким ставкам это становится узким местом даже при облегченной обработке трафика из-за ограниченное количество циклов CPU, доступное на пакет. Равномерно распределить трафик из одного интерфейса в несколько потоков (т.н. каналов или очередей), при этом сохранение непрерывности потока обычно является лучшим вариантом для масштабирование производительности, если наше приложение предназначено для работы с несколькими потоками или процессами и работают на нескольких ядрах CPU.

RSS (масштабирование на стороне приема)

Почти все Intel (и другие вендоры) NICs имеют поддержку RSS, это означает, что они способны аппаратно хешировать пакеты, чтобы распределить нагрузку между несколько очередей RX. В некоторых случаях RSS недоступен или негибок. достаточно (например, необходима пользовательская функция распределения), и ее можно заменено распространением программного обеспечения с помощью ZC.

Чтобы настроить количество очередей, вы можете использовать параметр RSS по адресу insmod time (если вы устанавливаете драйверы PF_RING ZC из пакетов, вы можете используйте файл конфигурации, как описано в инструкции по установке), передав разделенный запятыми список чисел (по одному на каждый интерфейс) (количество очередей на интерфейс). Примеры:

Включите столько очередей, сколько процессоров на каждом интерфейсе:

insmod ixgbe.ko RSS=0,0,0,0

Включите 4 очереди RX на интерфейс:

insmod ixgbe.ko RSS=4,4,4,4

Отключить множественную очередь (1 очередь RX на интерфейс):

insmod ixgbe.ko RSS=1,1,1,1

В качестве альтернативы можно настроить количество очередей RX во время выполнения. используя эттул:

ethtool --set-channels <if> combined 1

RSS распределяет нагрузку между указанным количеством очередей приема на основе хеш-функция, основанная на IP (или на основе IP/порта в случае TCP), в комбинации с таблицей косвенности: очередь = indirection_table[хэш(пакет)] Вы можете просмотреть содержимое таблицы косвенности с помощью:

ethtool -x <if>

Таблицу косвенности можно настроить, просто применив веса. в каждую очередь приема с помощью ethtool. Например, если мы хотим, чтобы весь трафик направлялся на очередь 0, и мы настроили карту с 4 очередями приема, мы можем использовать команду ниже:

ethtool -X <if> weight 1 0 0 0

При использовании PF_RING ZC RSS перенастраивается драйвером PF_RING ZC на большинстве Intel. семейства адаптеров. Однако на некоторых адаптерах (например. лед адаптеры) PF_RING ZC сохраняет конфигурация RSS, созданная драйвером Linux и ethtool, должна использоваться для настроить параметры RSS. Например, чтобы установить хеширование пакетов на основе четырехкортежа на лед адаптеры, которые являются IP-адресом источника и назначения и портом (по умолчанию), можно использовать:

ethtool -N enp1s0f1 rx-flow-hash tcp4 sdfn
ethtool -N enp1s0f1 rx-flow-hash udp4 sdfn

Или установить хеширование пакетов на основе двухкортежей, которые представляют собой только IP-адреса источника и назначения. можно использовать:

ethtool -N enp1s0f1 rx-flow-hash tcp4 sd
ethtool -N enp1s0f1 rx-flow-hash udp4 sd

Где в «sdnf» и «sd»:

  • s: IP-адрес источника

  • d: IP-адрес назначения.

  • f: Исходный порт

  • n: порт назначения

RSS с GTP

Когда дело доходит до масштабной обработки трафика GTP и мы хотим использовать RSS распределить нагрузку по обработке пакетов, используя базовую конфигурацию RSS часто не является жизнеспособным решением. Предположим, например, что мы хотим обработать GTP-C трафик с использованием выделенного процесса и балансировка нагрузки GTP-U трафик для несколько процессов или потоков: это возможно с использованием расширенной конфигурации RSS в сочетании с управлением потоком. Чтобы добиться этого, просто выполните следующие действия:

  1. Настройте карту с 8 (или любым количеством) очередей RX.

ethtool --set-channels <if> combined 8

2. Отправьте весь трафик GTP-C в первую очередь. Для этого мы используем директор потока, поддерживается большинством адаптеров Intel (например, E810) и NVIDIA/Mellanox (ConnectX).

ethtool -U <if> flow-type udp4 src-port 2123 action 0

(Примечание: «действие 0» означает «перейти в очередь 0»)

  1. Распределите весь трафик, отличный от GTP-C, по другим очередям.

ethtool -X <if> weight 0 1 1 1 1 1 1 1

(Примечание: трафик распределяется по очередям с весом != 0)

Соглашение об именах

Чтобы открыть конкретную очередь интерфейса, вам необходимо указать идентификатор очереди. используя суффикс «@<ID>». Пример:

pfcount -i zc:eth1@0

Обратите внимание, что если вы настраиваете интерфейс с несколькими очередями RSS и вы открываете его с помощью ZC с помощью zc:eth1, это то же самое, что открыть zc:eth1@0. Это не применяется в стандартном режиме ядра, где ядро абстрагирует интерфейс и захват из eth1 означает захват из всех очередей. Это происходит потому, что ZC — это технология обхода ядра, поэтому абстракции нет, и приложение напрямую открывает интерфейсную очередь, соответствующую полный интерфейс только при RSS=1.

PF_RING Кластер (Ядро)

Поскольку не все сетевые адаптеры поддерживают RSS для распределения нагрузки между несколько очередей RX на аппаратном уровне, модуль ядра PF_RING реализует механизмы именованная кластеризация для разделения и балансировки нагрузки между процессами. Это означает, что разные приложения, открывающие сокеты PF_RING, могут привязать их к конкретный идентификатор кластера (через pfring_set_cluster) для объединения сил и каждого анализировать часть пакетов. Способ распределения пакетов по сокетам кластера указан в кластере. политика. Политика по умолчанию — для каждого потока (т. е. все пакеты, принадлежащие одному и тому же 5-кортеж <proto, ip src/dst, port src/dst>), однако есть несколько вариантов. Это Таким образом, все пакеты, принадлежащие одному потоку, будут отправляться в одно и то же приложение, сохраняя логика приложения по мере трафика будет согласованной. Пример кластеризации ядра предоставлен pfcount:

pfcount -i eth1 -c 10 -H 5

Где:

  • -c 10 указывает идентификатор кластера

  • -H 5 определяет политику балансировки нагрузки:

    • 1 - круговой

    • 2 - исходный ip, dst ip

    • 3 - src ip, src port, dst ip, dst port

    • 4 - src ip, src port, dst ip, dst port, proto (по умолчанию)

    • 0 - IP-адрес источника, порт источника, IP-адрес DST, порт DST, прототип, vlan

    • 5 - src ip, src port, dst ip, dst port, proto для TCP, src ip, dst ip в случае отказа

    • 7 - туннелированный src ip, dst ip

    • 8 - туннелированный исходный ip, исходный порт, dst ip, dst порт

    • 9 — туннелированный src ip, src port, dst ip, dst port, proto (по умолчанию)

    • 6 - туннелированный исходный IP-адрес, исходный порт, dst IP, dst-порт, прото, vlan

    • 10 - туннелированный src ip, src port, dst ip, dst port, proto для TCP, src ip, dst ip в случае отказа

Примечание. Кластеризацию ядра нельзя использовать в сочетании с драйвером ZC, поскольку ZC является технология обхода ядра.

Кластер ZC (zbalance_ipc)

Бывают случаи, когда RSS нельзя использовать для балансировки нагрузки трафика, потому что:

  • он не всегда доступен (например, если вы не используете адаптер Intel)

  • для некоторых случаев использования он недостаточно гибок и необходима специальная функция распределения (например, туннелированный трафик, такой как GTP)

  • когда один и тот же трафик необходимо доставить в другое приложение, но мы используем ZC, который блокирует сетевой интерфейс (мы не можем позволить нескольким приложениям перехватывать трафик с одного и того же интерфейса одновременно)

  • когда один и тот же трафик необходимо доставить в другое приложение, но нам нужно разное количество потоков для каждого приложения (например, мы хотим распределить нагрузку по 4 экземплярам nProbe для генерации Netflow и 1 экземпляру n2disk для записи трафика)

В вышеописанных ситуациях RSS можно заменить распространением ПО с помощью ZC. либо написать собственное приложение поверх ZC API, либо использовать zbalance_ipc приложение, распространяемое с PF_RING. zbalance_ipc это процесс который можно использовать для перехвата трафика с одного или нескольких интерфейсов, и пакеты балансировки нагрузки для нескольких потребительских процессов. Обратите внимание, что для использования zbalance_ipc, RSS должен быть отключен.

Пример агрегации трафика с 2 интерфейсов и балансировки нагрузки на 2 процессы, использующие хэш на основе IP:

zbalance_ipc -i zc:eth1,zc:eth2 -n 2 -m 1 -c 10 -g 1

Где:

  • -n указывает количество исходящих очередей

  • -m выбирает хэш-функцию (доступно несколько вариантов или можно написать собственную)

    • 0: циклический (по умолчанию)

    • 1: IP-хеш

    • 2: Разветвление

    • 3: Разветвление (1-е место) + Круговая система (2-е, 3-е и т. д.)

    • 4: GTP хэш (внутренний IP/порт или GTP-C Seq-Num)

    • 5: GRE хэш (внутренний или внешний IP)

    • 6: Интерфейс X для постановки в очередь X

  • -g — это основное соответствие для потока захвата/распределения.

  • -c указывает идентификатор кластера ZC

В приведенном выше примере создаются 2 потока, которые могут быть открыты потребительским приложением. в качестве стандартных интерфейсов PF_RING (zc:10@0 и zc:10@1). Пример:

nprobe -i zc:10@0
nprobe -i zc:10@1

Аналогичным образом можно распределить трафик по нескольким приложения, каждое из которых имеет несколько потоков/процессов:

zbalance_ipc -i zc:eth1,zc:eth2 -n 2,1 -m 1 -c 10 -g 1

Где -n 2,1 означает:

  • распределить нагрузку по 2 очередям

  • отправить полную копию трафика еще в 1 очередь

Это тот случай, когда nProbe и n2disk обрабатывают один и тот же трафик:

nprobe -i zc:10@0
nprobe -i zc:10@1
n2disk -i zc:10@2 -o /storage

Использование ZC Cluster с systemd

zbalance_ipc можно управлять с помощью системаctl по операционным системам и дистрибутивы, использующие системный менеджер сервисов, настройка кластер услуга поставляется вместе с пфринг упаковка.

Поскольку часто требуется несколько кластеров, несколько экземпляров кластер служба может работать на том же хосте. Для управления конкретным кластером <экземпляр> добавить @<экземпляр> к кластер название услуги. Обычно <экземпляр> соответствует идентификатору кластера (например, 10 в примеры выше). <экземпляр> однозначно идентифицирует услугу и ее соответствующий файл конфигурации, который находится под /etc/cluster/cluster-<экземпляр>.conf.

Например, чтобы начать кластер например, можно создать следующее файл конфигурации, содержащий все параметры командной строки (см. -h) один за строку. Пример:

cat /etc/cluster/cluster-10.conf
-i=zc:eth1
-n=2,1
-m=1
-c=10
-g=1

А затем запустите службы с помощью:

systemctl start cluster@10

При желании можно включить запуск службы при загрузке с помощью:

systemctl enable cluster@10

Статус услуги можно контролировать с помощью:

systemctl status cluster@10

При использовании кластера для подачи nprobe или n2disk настоятельно рекомендуется использовать следующую схему именования, чтобы сделать явными зависимости служб:

APPLICATION-cluster_CLUSTERID-INSTANCEID.conf

Например, при использовании nprobe и присоединении к очереди 0 кластера 10 конфигурации путь к файлу будет:

/etc/nprobe/nprobe-cluster_10-0.conf

Услугой можно управлять с помощью:

systemctl status nprobe@cluster_10-0

Также предусмотрена утилитаusterctl для упрощения управления службами кластера. и зависимости.

Usage: clusterctl {start|stop|restart|status|start-deps|stop-deps} [cluster ID(s)]

Например, чтобы запустить все включенные службы кластера:

clusterctl start

Или перезапустить все службы (например, nprobe), требующие определенного экземпляра кластера (ID = 10):

clusterctl stop-deps 10
clusterctl start-deps 10

Если идентификатор кластера опущен, указанное действие будет применяться ко всем экземплярам кластера.
