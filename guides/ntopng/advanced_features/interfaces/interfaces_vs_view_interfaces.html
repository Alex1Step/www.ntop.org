3.3. Интерфейсы против интерфейсов просмотра

Бывают случаи, когда несколько интерфейсов необходимо объединить вместе с целью выполнения анализа трафика в совокупности.

Например, когда RSS используется для обработки пакетов в нескольких очередях, повторное агрегирование полезно для получения видимости всего трафика, а не только его части.

В следующем примере view: интерфейс создан для агрегирования пакетов из двух eth1 Очереди RSS обрабатываются с помощью копирования PF_RING Zero.

./ntopng -i zc:eth1@0  -i zc:eth1@1  -i view:zc:eth1@0,zc:eth1@1

Если вы не хотите перечислять все интерфейсы, вы можете использовать ярлык view:all чтобы указать ntopng создать интерфейс просмотра из всех настроенных интерфейсов. Приведенный выше пример станет:

./ntopng -i zc:eth1@0  -i zc:eth1@1  -i view:all

Однако интерфейсы представления имеют некоторые ограничения видимости по сравнению с другими интерфейсами. Это означает, что у них нет всех данных о трафике, которые обычно доступны для обычных интерфейсов. Например, интерфейсы представления не имеют:

  • MAC-адреса и все, что связано с MAC-адресами

  • Распределение пакетов по размерам (до 128, до 256, …)

  • TCP Флаги/Распределение ARP

Полный список всех ограничений доступен по ссылке. эта страница.

Использование представлений интерфейсов также уменьшает объем данных, доступных на просмотрено интерфейсы. Например, используя -i view:zc:eth1@0,zc:eth1@1 автоматически уменьшит объем данных, хранящихся для zc:eth1@0 и zc:eth1@1, соответственно.

Просматриваемые интерфейсы имеют только потоки. Все остальные сетевые элементы сохраняются только для интерфейса просмотра. Неисчерпывающий список сетевых элементов, которые отсутствуют в просматриваемых интерфейсах, но сохраняются в интерфейсе просмотра:

  • Хосты и исторические данные хостов

  • Автономные системы

  • VLAN

Обоснование этого следующее:

  • Технический, поскольку сохранение большинства сетевых элементов только в представлении значительно снижает общий объем памяти.

  • Практично, чтобы избежать хранения частичных данных (например, одного и того же хоста). 1.1.1.1 можно увидеть на двух интерфейсах, но, поскольку используется представление, предполагается, что только его общие агрегированные данные являются релевантными).
