Мониторинг

nDPI обычно требуется всего несколько пакетов на поток, чтобы получить полную классификацию и получить все необходимые метаданные/flow_risks. После этого nDPI прекращает обработку потока. Однако в некоторых случаях может оказаться полезным разрешить nDPI обрабатывать весь поток (т.е. все свои пакеты, без каких-либо ограничений). Несколько примеров:

  • для извлечения всех метаданных STUN из потока STUN

  • для извлечения всех пар запрос/воспроизведение из потока DNS

По сути, мониторинг позволяет приложению получать одни и те же метаданные несколько раз в течение всего сеанса.

Если мониторинг включен в потоке:

  • структуры ndpi_flow->protos, ndpi_flow->http, ndpi_flow->stun, … заполняются как обычно, обычно первый экземпляр конкретных метаданных. Ничего не изменилось.

  • пакет за пакетом, новая структура ndpi_flow->monitor заполняется метаданными текущий пакет. Эта информация теряется при начале обработки следующего пакета в том же потоке; ответственность за его получение лежит на приложении.

Другими словами:

  • «Метаданные потока» сохраняются в ndpi_flow->protos, ndpi_flow->http, ndpi_flow->stun, независимо от того, включена или нет функция мониторинга. Эти поля всегда доступны.

  • «(текущие) метаданные пакета» сохраняются в ndpi_flow->monitor, только если монитор включен.

Мониторинг должен быть явно включен, например: --cfg=stun,monitoring,1. Чтобы включить/отключить мониторинг для всех протоколов, вы можете использовать --cfg=any,monitoring,1 но сейчас поддерживаются только STUN и S7COMM.

Поскольку мониторинг процессов все потоковых пакетов, это может повлиять на производительность.

Замечания по реализации

  • Потоки переходят в состояние мониторинга только после окончания экстрадиссекций.

  • Классификация не меняется для потоков в состоянии мониторинга.

  • Вероятно, нам нужно улучшить реассемблер TCP, чтобы лучше обрабатывать потоки TCP в состоянии мониторинга.
